# Research notes 2026-10-21 (sources fetched on that date; vendor help pages show no publish date; items marked UNVERIFIED were not confirmed)

## A. Trash with a timer (used for the Trash timer feature, migration 0014)
- Outline: fixed 30 days, hourly cleanup task in batches, re-checks `deletedAt` right before destroying, UI computes "deleted in N days" (client side). github.com/outline/outline server/queues/tasks/CleanupDeletedDocumentsTask.ts, server/commands/documentPermanentDeleter.ts.
- Docmost: per-workspace `trashRetentionDays` (default 30), purge by 24 h interval. github.com/docmost/docmost apps/server/src/core/page/services/trash-cleanup.service.ts.
- BookStack: `recycle_bin_lifetime` default 30, `0` disables the bin, `-1` keeps forever; retention counts from a separate Deletion record; restore of a child whose parent is trashed does nothing (a pitfall). github.com/BookStackApp/BookStack app/Config/app.php, app/Entities/Tools/TrashCan.php.
- Notion 30 days (Enterprise owners can change), Google Drive/Gmail 30 days, GitHub deleted repositories 90 days, Linear 30 days, Confluence: no auto purge in cloud trash (UNVERIFIED for space-level purge). No product offers a per-item timer: ours does (one item, a selection, everything).
- Applied: `purge_after` is stored per row at delete time (changing the setting never silently moves old items; the owner can apply a new timer to everything on purpose); NULL = keep until deleted by hand; DB clock only; purge in batches of 200 with `FOR UPDATE SKIP LOCKED` and the same conditions re-checked in the delete; a purge date never set for live rows; every purge is logged by the delete trigger.
- Not applied (not needed yet): a "protected" flag, subtree cascade ids (documents have no children yet), restore-time name collision handling (refs are unique across trashed rows, so no collision can occur), background-job "empty trash" with rate limit.

## B. Organizations > projects with invited-only access (for the later multi-project step; design only)
- Supabase guides (RLS, performance, functions, custom claims): wrap `auth.uid()` as `(select auth.uid())`, index every column a policy uses, put security-definer helpers in a non-exposed schema with `search_path=''` and revoke execute from public/anon, name the role with `to authenticated`, views need `security_invoker=true`. Custom-claims RBAC (auth hook, Beta) keeps ONE role per user in the JWT and goes stale after a revoke (inference): prefer membership tables for invite-only access. supabase.com/docs/guides/database/postgres/row-level-security, .../api/custom-claims-and-role-based-access-control-rbac, .../database/functions.
- Docmost: `spaces.visibility` default private, `space_members` (user or group, role), `workspace_invitations` (email, role, token). Application-layer checks, not RLS. Outline: private collection needs membership, team admins can read any non-personal collection. Cal.com: `Membership.accepted` default false, role MEMBER/ADMIN/OWNER. BookStack: could not fetch (UNVERIFIED). Basejump (Supabase teams starter) is marked unmaintained by its README.
- Recommended minimal schema: profiles; orgs; org_members(org_id,user_id,role owner|admin|member, index user_id); projects(org_id); project_members(project_id,user_id,role manager|editor|viewer, index user_id); documents(project_id, org_id with a composite FK); invites(org_id, project_id null, email, roles, token_hash, expires_at, accepted_at, revoked_at, partial unique on pending); ai_tokens + ai_token_projects as a SEPARATE principal (never an org member). No public reference exists for the AI-token design (UNVERIFIED), review it on its own.
- Helper design: `private.org_role(org)`, `private.is_org_admin(org)`, `private.project_role(project)` (returns manager for org admins = the admin override in one place), `private.my_project_ids()`. Keep our existing `private.can_read_project` / `private.can_edit_project` as the only functions policies call.
- Invitation flow: create_invite RPC (admin/manager) -> emailed random token, only its hash stored -> `accept_invite(token)` definer RPC requires a verified email match, unexpired, unrevoked, idempotent, inserts org+project membership in one transaction; leaving an org removes its project memberships; guard the last owner with a trigger.
- Pitfalls: policy recursion (use helpers), definer functions exposed through RPC, slow policies (bare auth.uid(), no index), views bypassing RLS, Realtime DELETE events not RLS-filtered and revoked users keep receiving until the JWT expires, storage policies on `storage.objects` only, stale JWT claims, invite abuse / self-promotion (missing `with check`).
- Test matrix (pgTAP via `supabase test db`, helpers from usebasejump/supabase-test-helpers, maintenance UNVERIFIED): personas owner, admin, invited manager/editor/viewer, member not invited, member of another org, anon, pending invitee, removed member, scoped/unscoped/revoked AI token; operations SELECT/INSERT/UPDATE/DELETE on every table, RPCs, views, storage, Realtime; assert `rls_enabled` on all public tables.
