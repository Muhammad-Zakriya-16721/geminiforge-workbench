## Bottom line
docs/04 is right in direction but outdated in four places: Supabase OAuth is now verified as a public beta; Client ID Metadata Documents (CIMD) are missing; there is no per-client matrix (most clients can send an Authorization header, so path tokens are only needed for the Gemini app); the Supabase OAuth risk that tokens carry full user privileges is not mentioned. Phase 6 order is wrong: verifying clients (6.6) must come BEFORE OAuth (6.5). The path token is acceptable only as a labelled, short-lived, read-only fallback.

## MCP status (VERIFIED, modelcontextprotocol.io/specification/2026-07-28/...)
Latest revision 2026-07-28: stateless (Mcp-Session-Id and initialize removed, `server/discover` added), tasks moved to an extension, multi round-trip `input_required`, `tools/list` results carry `ttlMs` and `cacheScope`, Dynamic Client Registration (DCR) deprecated in favour of CIMD, clients must validate `iss` (RFC 9207), HTTP+SSE deprecated. Authorization: the server is an OAuth 2.1 resource server with Protected Resource Metadata (RFC 9728); clients send RFC 8707 `resource`; servers validate audience and never forward tokens; tokens go in `Authorization: Bearer` and MUST NOT be in the query string; 401 with `WWW-Authenticate` carrying `resource_metadata`. ## Attacks and mitigations
Official page /specification/2026-07-28/basic/security_best_practices (VERIFIED): confused deputy, token passthrough, SSRF, state hijack, OAuth URL injection, mix-up, localhost redirect impersonation, CIMD trust, scope minimization. We are not a third-party proxy, but with Supabase as authorization server our consent page must name the client and redirect URI, have CSRF protection, anti-framing headers and exact redirect matching; enabling CIMD means we fetch client URLs (SSRF). Tool poisoning/rug pull: practitioner write-ups only (SNIPPET: Willison 2025-07-06, Zuplo, Invariant); mitigation = pin tool definitions by hash on the client. Our real risk is OUR documents as the injection channel (lethal trifecta). Missing in docs/04: exfiltration through rendering — Markdown in proposals can carry remote images/links; if the Review inbox auto-loads them, injected text can leak content before a human accepts.

## Tokens
GitHub format (VERIFIED github.blog): type prefix + underscore + 32-bit CRC32 checksum in the last 6 characters, base62; prefix alone cuts false positives to ~0.5%. Partner secret-scanning programme needs a public HTTPS verifier endpoint: too heavy for a solo project; use the format and a gitleaks rule. OWASP: credentials must not be in URLs (logs). SHA-256 of a high-entropy token is adequate (judgement). Path token: Supabase edge logs and Vercel logs contain it (retention unconfirmed) -> only read-only, 24 h to 7 d, low daily limit, one per client, revoked on rotation.

## Supabase Auth OAuth 2.1 server (VERIFIED supabase.com/docs/guides/auth/oauth-server/..., changelog 38022)
Public beta (GA target Q4 2025 passed; no GA notice found — check live docs). Available on all plans; signed-in users count to MAU. You supply the consent page ("Authorization Path"). PKCE S256 required; DCR off by default; no CIMD documented. Phase 1 has no scopes: tokens carry full user privileges and rely on RLS, so a leaked MCP token is a normal user JWT that works against PostgREST. `aud` changes only via a custom access token hook; RFC 8707 `resource` not mentioned. Documented defences: RESTRICTIVE RLS on `auth.jwt()->>'client_id' IS NOT NULL`, and an `aud` hook that rejects unknown clients. Access tokens 3600 s, refresh rotates; HS256 default (RS256/ES256 recommended).

## Ranked changes
1 (S) run client verification first (Claude Code, Cursor, claude.ai, Gemini app), then make `header` the default token kind and `path` the exception. 2 (S) sanitise the Review inbox: no remote images, link targets as text, diffs as plain text. 3 (S) token format `gfk_…` + CRC32 base62 checksum, show last 4 characters, gitleaks rule in CI. 4 (M) docs/04 items 1-2: two token kinds, rotation with overlap, path tokens 24 h by default. 5 (M) per-token tool and document allow-lists; static tool descriptions; expose a hash of the tool list. 6 (M) OAuth stage: enable Supabase OAuth server with DCR, write consent page (client name, exact redirect URI, CSRF, anti-framing), RESTRICTIVE RLS for `client_id IS NOT NULL`, custom access token hook setting/checking `aud` and rejecting unknown clients, Edge Function returns 401 + `resource_metadata` and validates aud/client_id/iss, keep manual tokens as fallback, test with Claude Code and claude.ai. 7 (M) review friction: reason required for high-risk accepts, no bulk accept for them, auto-accept only a narrow class. 8 (M) invitee data purge/export/delete, log retention. 9 (M) hash-chained audit log + weekly head emailed to an external mailbox. 10 (M) anomaly alerts + auto-pause. 11 (L) support spec 2026-07-28 once the clients you use adopt it. Defer: two-person approval, GitHub partner programme.
Risk: building the OAuth stage on a beta feature with full-privilege tokens and no RESTRICTIVE RLS would widen exposure beyond today's read-only path tokens.
