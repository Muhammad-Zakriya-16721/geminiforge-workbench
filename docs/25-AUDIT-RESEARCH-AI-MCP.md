## 2. Wrong, overstated, or UNVERIFIED
1. **"Support MCP 2026-07-28 now, dual-version" is already done.** Our function uses `@modelcontextprotocol/server` 2.3.1 `createMcpHandler` (stateless), sets `cacheHints` (`ttlMs`, `cacheScope`) and `server/discover`, and `test.mjs` proves a legacy `initialize` with 2025-06-18 still answers and `GET` returns 405. Plan 6.12 ("once the clients adopt it") is stale: mark done; remaining work is tests for `UnsupportedProtocolVersionError`, `HeaderMismatch` and the Origin rule.
2. **"ChatGPT Plus is not eligible for custom MCP: CONFIRMED" is NOT confirmed.** OpenAI's pages were unreachable for me (help.openai.com 403, developers.openai.com doc 404) and third-party pages conflict (some: Plus/Pro read-only developer mode; some: workspace plans only; write actions unclear). Status: UNVERIFIED. Cheapest truth: you check ChatGPT Settings > Apps & Connectors > Advanced > Developer mode on your Plus account (2 minutes). Either way ChatGPT stays off the critical path.
3. **Origin validation is a spec MUST and we do not do it** (report is right; I verified the spec text). Our `makeFetch` answers every request, sends `Access-Control-Allow-Origin: *` and never checks `Origin`. The SDK exports `originValidationResponse` and `hostHeaderValidationResponse` helpers. Risk is low (bearer token required, no cookies, public server) but it is a compliance gap and trivial to fix.
4. **IP "hashing" is reversible**: `ipOf` is SHA-256 of a fixed public string plus the IP, cut to 64 bits; an attacker with the DB can enumerate all IPv4 addresses (2^32). It is pseudonymisation, not anonymisation. Use HMAC with a secret kept in the function environment (and rotate) or store nothing.
5. **Report overlooked what we already have** (so its "boring tool surface" proposal is mostly satisfied): static tool descriptions; 12 tools (`list_projects`, `get_guide`, `get_outline`, `search_docs`, `read_doc`, `get_references`, `query_dataset`, `get_changes`, `propose_changes`, `propose_edit`, `list_drafts`, `get_draft`); all document text wrapped in `<untrusted-docs id=...>` with the closing tag protected; zero-width/bidi/tag characters stripped by `clean()` (covers its test H-06); response cap 24,000 characters (already below its 48-64 KiB suggestion); `read_doc` max 20 documents; token only from the path or an `Authorization: Bearer dk_...` header (a query-string token is ignored, covers H-15); proposals carry `base_rev` and an idempotency key; anonymous callers get no write tools. Missing from the report's list and from ours: a tool-manifest hash, `get_section` (needs `doc_chunks`), opaque cursors (we use offsets; acceptable at our size).
6. **Groq numbers unverified**: the Groq page I fetched shows "Developer plan" base limits for a few models and says nothing about Free or card requirements, so the report's "30 RPM, 1,000 RPD, no-training" row stays UNVERIFIED. Cerebras and Hugging Face credit ($0.10) figures also not re-verified. None is needed.
7. Report says the Gemini documentation lists DCR and an Advanced credentials path but "does not document an arbitrary static Authorization header". Verified. So the Gemini path token stays until the "Advanced features" credential path is tested; Claude (static headers supported) is the clean header-token host.
8. Weekly "head hash emailed externally" (plan 6.9): the report calls it theatre without a hash chain. Partly fair; I agree to drop it until there is a chain, and keep the append-only log.
9. "Automation bias" effect sizes: no number, correct. "llms.txt is a convention, not a standard": correct, low stakes.
10. The report's Cloudflare/Workers "exit path" and 100k requests/day: not re-verified, not needed.

## 3. Decisions adopted
1. **Primary Q&A = in-app extractive passage finder (no model), secondary = Gemini app + our read-only MCP** (owner-accepted consumer-cloud path, labelled as such in the UI and docs). No free API ever receives private text (Google unpaid tier has human review; Mistral free may train). NotebookLM stays a manual reading aid. Browser LLM (WebLLM 0.2.86, desktop only, multi-GB download) stays an experimental opt-in after the core works.
2. **Retrieval**: `doc_chunks` derived from `docs.body` (never rewrite stored whitespace): H1-H3 sections, heading path searchable, paragraph-boundary splits by a character cap (no tokenizer), exact start/end offsets into the current body, weighted `tsvector` (title/heading high), GIN; two lanes: FTS (`websearch_to_tsquery`) and a literal-substring lane for identifiers/versions/paths; optional `pg_trgm` later; verified state is a small tie-break only. Embeddings only if the golden set fails.
3. **Golden set = 40 questions, fixed**: 22 single-document facts (8 exact identifiers/numbers; gold chunk in top 6 for at least 21/22), 6 cross-document (at least 5/6 complete), 4 paraphrase (at least 3/4), 6 unanswerable (6/6 refuse), 2 injection (evidence found, injected instruction ignored); quote validity must be 100%; embedding trigger: miss more than about 2 of the 34 answerable/adversarial cases or repeatedly fail the paraphrase slice. Targets are policy, not standards.
4. **Quote verification**: model proposes claim + chunk id + candidate quote; server locates it (exact substring first; normalisation only to LOCATE, with an index map); UI shows the substring sliced from the stored revision at the original offsets, never the model's copy; three checks (existence, attribution, support; only the first two are deterministic). **Remove the 6-word minimum** (short exact identifiers such as "24 hours" must pass), keep a maximum (about 80 words). Source chips open a panel: document, heading, revision, verification state, highlighted quote as plain text.
5. **Review inbox**: proposal -> deterministic risk class -> visual diff + linear Changes list -> per-hunk decisions stored in our tables (not in CodeMirror) -> final check `current_rev = base_rev` -> apply -> audit -> reversible revision. Risk classes Low / Medium / High (auth, permissions, privacy, RLS, sharing, secrets, token lifetimes, commands, SQL/migrations, deletion, check marks) / Blocked-from-auto-accept (plan completion, destructive ops, access control, external URLs, security policy, flagged injection). High = reason required, no bulk accept. Auto-accept stays off. Metrics: post-accept undo rate, reversal within 7 days, high-risk rejection rate, stale-proposal rate, review time, queue age, per-token accept/reject.
6. **Tokens**: show a digest-derived fingerprint (first 8 hex of SHA-256 of the token) instead of the "last 4" of a checksum suffix (plan 6.3); today's tokens are `dk_` + 64 hex. Defaults (policy): Gemini path reader 24 h; header Reader 30 days; header Writer (propose only) 7 days; debug at most 1 h. Anomaly signals: use after long idle, call-volume spike, first use of a new tool class, repeated denied reads, repeated malformed proposals, path token past expiry. Kill switch checked before retrieval and before proposal insert.
7. **Protocol hygiene**: keep stateless 2026-07-28 + legacy initialize; reject JSON-RPC batches; Origin 403 when present and not allowlisted (empty allowlist by default; Inspector origins added only in a test environment) and drop `Access-Control-Allow-Origin: *`; host check; tool-manifest hash (canonical names, schemas and descriptions) published in `get_guide` and checked in CI; tool descriptions stay static code; sampling, elicitation, Tasks, MCP Apps, OAuth stay on hold.
8. **Content-gap log (3b.9/7.4)**: raw questions are private data: owner-only table, 90-day retention unless promoted to a task.
9. **Deterministic AI-assisted features first**: stale-content detection, "why this changed" from the proposer's note, broken internal links on save, content gaps, change digest, duplicate detection (hash/title/optional trigram), glossary candidates; Gemini on demand for summaries and step suggestions, always as proposals.
