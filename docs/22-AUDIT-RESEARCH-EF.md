## 3. Defects in the report's sample code (do NOT copy as is)
1. `backup.yml` weekly drill condition `github.event.schedule == '23 1 * * 0'` can never be true: only one cron (`23 1 * * *`) is declared, so the "weekly" restore test would run only on manual dispatch. Fix: one daily cron and decide inside the job (`date -u +%u` = 7).
2. The restore test loads `schema.sql` and `data.sql` into a plain `postgres:17` service and skips `roles.sql`. Our schema references roles `anon`, `authenticated`, `service_role`, the `auth` schema (`auth.uid()`, FKs to `auth.users`) and extensions (pgcrypto in schema `extensions`, supabase_vault, pg_cron). On vanilla Postgres this fails at the first policy. The test must restore into a Supabase-shaped target: either `supabase start` (local stack, accurate, a few minutes) or a vanilla container plus a small prelude that creates those roles, schemas and `auth.users`. Pick after inspecting the first real dump.
3. `npm install --global supabase` is not the documented route (docs describe a per-project dev dependency, version pinned). Use the official `supabase/setup-cli` action (already in plan item 9.6), pinned by commit SHA, with a pinned CLI version.
4. `actions/checkout@v4`, `actions/upload-artifact@v4` use floating tags and checkout is not needed at all. Our rule (plan 9.5): pin every third-party action by full commit SHA; drop checkout.
5. `curl https://rclone.org/install.sh | sudo bash` is exactly the supply-chain pattern we ban. Use the distro package (`apt-get install rclone`) or a pinned release zip with a checked SHA-256.
6. `SUPABASE_DB_URL` must be the **session pooler** string (user `postgres.<project-ref>`, port 5432, host copied from the Connect dialog), not the direct host (IPv6 only). The report says this in prose but the workflow gives no hint.
7. Env names in `/api/ops-keepalive.ts` (`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`) differ from the ones already used by `api/invite.ts` (`VITE_SUPABASE_URL || SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY || SUPABASE_PUBLISHABLE_KEY`). Reuse the existing lookups; no new variables on Vercel.
8. Healthchecks pings only on success. Add a `/fail` ping on failure (faster alert than waiting for the grace period) and a `/start` ping for duration.
9. The artifact upload happens before the B2 upload and the job has no `environment:`; put the secrets in a GitHub Environment limited to `main` so only `main` workflow runs can read the DB password and B2 key.
10. `ops_keepalive` migration is fine (explicit GRANT, which the 2026-10-30 change requires). Add: the table gets no sequence; keep it out of the Realtime publication; add it to the grants test.
11. Dump role: the report uses the `postgres` password. A narrower role would be better but dumping RLS-protected tables needs a role that bypasses RLS (otherwise rows are silently omitted or the dump errors). Whether the managed `postgres` role can create such a role is UNVERIFIED; v1 uses `postgres` with the password stored only as an Environment secret; revisit.

## 4. Adopted design (what goes into the master plan)
1. **Keep-alive (9.2):** table `public.ops_keepalive` (one row, public read, no writes), read by (a) a Vercel cron `/api/ops-keepalive` once daily and (b) a GitHub Actions schedule at a different hour. Both ping Healthchecks on success and `/fail` on error. Vercel's timing varies by up to 59 minutes, so the dead-man grace is at least 2 h. The GitHub schedule disables itself after 60 days without repo activity; the Vercel cron is the independent second source. The Supabase pause-warning email goes to a mailbox the owner reads.
2. **Monitoring (9.8):** UptimeRobot (HTTP check of the site and of a `/api/health` endpoint that really reads one row; 5 min) + Healthchecks (keep-alive x2, backup, storage export, restore drill). Two free accounts, one purpose each. An alert path that does not depend on the app's own email (owner's personal email and push).
3. **Backups (9.3):** nightly GitHub Actions job: session-pooler URL, three dumps, sanity checks (non-empty, row counts), restore into a Supabase-shaped target in the same job (weekly or every run if it is fast), write counts into the archive, `age` encrypt to the public recipient (private identity offline in two physical copies, never in GitHub), upload ciphertext as a 14-day artifact, copy ciphertext to B2, ping Healthchecks. Storage objects are exported by a separate script with a SHA-256 manifest, also encrypted before upload. Because the repo is public (D17) nothing unencrypted is ever uploaded and no counts/manifests are published as plain artifacts. Monthly: owner downloads one object from B2, decrypts offline, restores locally. Database and Storage exports are not one atomic snapshot (accepted for a few-user docs app).
4. **Email (2.14-2.18, 3.13, 3.15):** Gmail SMTP from Vercel remains the invitation path (Supabase Edge cannot use ports 25/587; Auth mail via custom SMTP is a separate Supabase service and is configured in the Auth dashboard). Quotas 3/hour and 10/day per organization, 3/day per recipient, invitation lifetime 72 h, the invite secret in the URL fragment with an explicit click, no tracking pixel, the GIF is optional decoration, the invite is fully understandable with images off, copy-link/mailto stays the fallback. A `safeMailDisplayName` sanitizer (strip CR, LF, control characters, quotes and angle brackets, cap length) is applied to the inviter name in the From display name.
5. **Exit plan (9.10):** no $0 drop-in Supabase replacement exists. Neon Free is the best database-only exit (restores plain SQL; Auth, PostgREST, Realtime and Storage would have to be rebuilt). Quarterly "exit drill": restore the latest backup into a throwaway Neon project and open the Markdown export. Static hosting exits (Netlify, Cloudflare Pages) stay as documented options only.

## 5. My additions beyond the report
- **Gmail account hygiene is a real trap:** app passwords need 2-Step Verification that is not "security keys only" and no Advanced Protection. A dedicated plain Gmail with an authenticator app or phone as 2SV works; then a later switch to keys-only or Advanced Protection silently breaks mail sending, and so does a Google password change (app passwords are revoked). Put both in the runbook, and make the first failed send visible in the app.
- **The pause-warning mail and the Supabase account:** the owner's Supabase account email must be one that is read; put it in the monthly checklist.
- **Backup restore doc requires** `session_replication_role = replica` and `--single-transaction` plus ON_ERROR_STOP; include in the runbook; custom role passwords are not in the dump.
- **Postgres version drift:** the dump is plain SQL and portable, but a Postgres-17-only `SET transaction_timeout` line exists in data dumps and breaks older targets; keep restore targets on 17.
- **Security of the backup path:** `age` recipient in a repository variable is public by design; the DB password and B2 key are Environment secrets; B2 application key restricted to one bucket, ideally without delete rights (UNVERIFIED which capabilities B2 offers; check when creating it); B2 bucket lifecycle rule for retention (check in the UI).
- **Test pack:** the report's 64 operations tests are kept as a checklist in `docs/22a` (lines starting at "operations test pack"); the first five to run are 1 (homepage), 14 (dump coverage of auth/storage/vault), 24-25 (storage export and SHA-256 manifest), 40 (scanner cannot accept an invite), 61 (public-repo confidentiality: nothing downloadable from CI artifacts is plaintext).
